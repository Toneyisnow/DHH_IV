**二、游戏定位与美术标准**

这是以航海贸易、角色培养、和连续剧情为核心的单人经营类游戏。

视觉参考我给定项目Assets目录下的各种图片，当生成新图片时，确保图片的风格一致。

具体要求：

- UI采用复古像素边框、清晰的中文字体、角色头像和整洁的信息窗口。
- 所有素材统一像素尺寸、视角、描边和色彩风格，不能呈现明显的随机素材拼贴感。
- 中文字体必须覆盖实际对白与菜单文字，不能出现缺字、乱码或溢出。

**世界与玩法循环**

- 基础时代氛围为架空的“大航海时代”，以历史港口、风土特产、贸易网络与传奇航海家的气质为灵感；不应将架空人物传记误称为真实史实。
- 核心循环：**选择家园港口→探索航道与风向→运送和交易原料→开设城市产业园及工厂→生产中间品/成品→供应当地市场或其他港口→赚取金币/声望/配方与伙伴→升级船队→开辟新航路、推进主线**。
- 玩家日常动力：厂房完成可领取/续产、不同港口的商品供求变化、限时商会委托、伙伴事件、探索与配方发现；不使用强制在线惩罚，也不设计退出游戏期间失去存货的陷阱。
- 首版不强制角色走遍所有城市方可通关；但最终挑战必须合理检验贸易、制造、航海和伙伴培养，不只检查金币总数。

## 游戏的几大核心玩法

### 一。人物造型塑造。

风格：使用素材种的”李华梅“的画风风格。(Assets\Screenshot_Reconstruction\generated\04_portrait.png)

**创建角色与角色数据**

- 十套基型建议：东亚男/女、欧洲男/女、西亚男/女、非洲男/女、南亚男/女；这些仅是初始外观模板，不锁定技能、职业、出生地或故事结局。每套提供不同脸型/站姿，所有选项均可跨模板自由组合。
- 可调层级：肤色6档、发型至少8类、发色6档、衣服主/辅色各8种、帽子/耳饰/披风/腰带/武器装饰。配饰不决定实际武器战斗力；功能装备在游戏中单独计算。
- 建立角色外观的**参数化配方**（baseId、skinId、hairId、hairColor、outfitId、primaryColor、secondaryColor、accessoryIds），保存参数及必要缩略图。避免只保存不可编辑的截图。
- 3D立绘和八方向行走图 (示例09_walk_sheet.png)可共用一套角色参数，通过预先制作的部件图层及动画集实现；如果有3D参考，最终输出按统一二维像素渲染方案处理。
- 出生前玩家从开放家园港中选择一个城市。开始时随机给予**3项不同的1级生产类技能**，重开可重新抽取；这3项技能应与现有八大产业相容，并在开场清楚展示。不因人物模板改变抽取概率。

### 二。商品及产业系统。

重点说明：游戏中的所有数值系统、运算公式系统均需要一套专属的代码文件夹，并给出每个定义、每个公式的详细说明，用词必须保持一致，具备晚上的测试用例，以及将来可能进行无界面的持久化模拟运行。


**商品与市场（核心已确认规则）**

- **八大产业固定**：农业、畜牧、纺织、林业、矿业、工业、奢侈品、化学/药剂。允许跨产业配方，但每一商品必须有主产业归属。

**城市初始库存（2026-10-15 补充）**

- **新游戏创建时，每座城市市场的非零库存只允许是 Raw 原材料（category=R），且只允许 Level 4、Level 5 品质。**Level 指商品品质，不是工坊等级或产业层级；S、1、2、3 品质的初始市场库存均为0。所有 M/C 商品及旗舰航海仪的初始市场库存均为0。
- 保留城市常供原料分布：仅本城原料供应列表中的 R 商品有初始库存，其他原料在该城初始为0；每种 R 至少由两个不同城市常规供应的规则保持不变。
- **对每座城市的每一种常供原料，Level 4 初始数量为同城同种原料 Level 5 初始数量的1%–20%。**比例的基数是新档创建时的 Level 5 数量，不是交易后的剩余数量，也不是全城商品总量。
- 当前实现默认值：Level 5 为100件，Level 4 在1–20件之间均匀随机取整数。一般计算为 `ceil(N5_initial × 0.01) ≤ N4_initial ≤ floor(N5_initial × 0.20)`；配置必须保证整数区间非空且总量不超过市场容量。100件是当前可配置默认值，Raw/品质限制与1%–20%的比例范围是本次确认的规则。
- 初始随机数使用新档种子，可复现；交易、界面刷新、存档读取不重新抽取初始数量。各品质分别记录和扣减，购买 Level 4 不得消耗 Level 5，售出商品保留原品质，市场总库存等于各品质库存之和。
- 本节约束**新档初始状态**。后续生产、交易及 NPC 补货按各自规则改变库存，可以出现其他品质及 M/C 商品；不能据此强制清空已有存档。
- 当前项目配套实现：家园赠送原料为 Level 5；新建自动运输订单默认使用 Level 5；无品质明细的旧档市场库存按原先的 Level 3 兼容读取，旧订单保留原品质。
- 配置入口：`Assets/Resources/Data/Economy/market.json` 的 `market.initialRawLevel5Stock`、`initialRawLevel4MinPercent`、`initialRawLevel4MaxPercent`；初始化入口：`Assets/Core/Data/GameService.Initialization.cs`。上述路径相对 Unity 项目 `MaritimeLegend/`。
- 验收：检查全部城市和商品的初始类别、品质及数量比例；覆盖多个种子及同种子复现、按品质买卖、缺货拒绝、存档重载和旧档兼容。

**市场供需与交易规则**

- **每座城市每种商品有独立的库存、供需压力、买卖价与最近交易统计**。建议的报价公式：`参考价 = basePrice × qualityFactor × citySpecialtyFactor × marketPressure`；`玩家买入价 = ceil(参考价 × (1 + spread/2))`；`玩家卖出价 = floor(参考价 × (1 - spread/2))`，spread默认0.12。成交价在交易执行时重新计算，不以旧UI报价结算。
- **确定的反刷机制**：在同一城市连续、大量**买入**某商品，城市卖给玩家的价格逐步**上涨**；连续、大量**卖出**某商品，城市从玩家处的收购价逐步**下降**。用库存/成交量改变市场压力，并以游戏时间和NPC交易缓慢均值回归。玩家不能反复在少数城市无限倒手获利。
- 建议计算模型（可调）：每种商品设置 `referenceStock`，每成交 `q` 件，供需压力 `p` 按 `delta=q/referenceStock` 更新；玩家买入 `p+=0.20×delta`，卖出 `p-=0.20×delta`，夹紧在[-0.45,+0.60]；`marketPressure=exp(p)`，每游戏内日向0回归15%。高频买卖必须逐笔计价或按批次积分，避免大单锁价绕过反刷。
- **NPC每小时向城市市场补充R原材料**；每种R必须至少在**两个不同城市**存在常规NPC供应，避免剧情卡死。NPC补货量以城市特产系数决定，受城市人口与天气等可选因素影响，不无限塞满。M/C主要由交易、城市NPC基础供给、工厂生产投放形成。
- 工厂成品可**自动投放市场**（设置价格策略、最小库存、最大单次上架量），但玩家不能自己挂单给自己刷声望或经验。单人版本由NPC供求撮合；未来多人版本由玩家订单簿/托管结算替换NPC撮合，市场核心接口保持稳定。
- 交易必须扣除真实库存、资金、舱容与手续费，失败原子回滚；若存档重载，不可重复领取、重复售卖或制造复制物品。

产业系统：通过公式：  

N个原料（可能是不同原料） + 技能 + 时间 = 加工品

N个加工品（可能是不同加工品） + 技能 + 时间 = 成品

**工厂、配方与品质**

- **配方是唯一可信的生产依据**。每个 `recipeId` 配置输入商品+数量、产出商品+数量、工厂类型、所需技能、最低技能等级、生产费用、基础时长、难度、解锁条件以及是否消耗模具/工具。工具若非消耗品，必须显式记录耐久度。
- 所有可批量生产的配方在首版均是可审计的**封闭配方表**。此前讨论的AI自由组合制造可作为后续扩展：AI仅提议“原料→工艺→候选物品”及低模/二维图稿，必须经**类型、质量守恒、材料属性、价值边界、技能等级、稀有度、命名唯一性**校验及审核后写入正式配方表；禁止任意Prompt直接创造永久有效的高价值产品。未来系统兼顾**灵活度与约束**。
- **「工艺」技能最高20级**。有效技能等级来自工厂主技能、当班伙伴技能、城市加成及玩家个人技能的规则化组合；建议 `effectiveLevel = clamp(factoryLevel + floor(partnerLevel×0.5) + cityBonusLevel, 1, 20)`，而不是把几个20级直接堆到60级。制造经验仅在**实际消耗原料并完工**时发放。
- **品质确认规则**：所有消耗原料中最差品质为 `base`；产出只能处于**S到base（含）**区间，绝不能比最差原料更差；从base向更高品质跃迁的概率**指数级递减**。技能等级提高时，提升高品质产出的概率，而不是改写品质边界。
- 推荐可测算法：品质映射 S=0、1=1、…、5=5（数字越小越好）；以 `baseIndex=max(inputs.qualityIndex)`，在候选 `q∈[0,baseIndex]` 之间按权重 `w(q)=exp(-λ×(baseIndex-q))` 抽取；`λ=max(0.55, 2.3 - 0.065×(effectiveLevel-1) + difficultyPenalty)`。注意技能升级使λ下降，提升跨档概率，而指数权重仍使S尤其稀少；同一生产订单独立抽样，禁止通过重载重复刷品质（存档保留随机种子和结果）。
- **每条工单有订单ID、原料锁定、开始与结束时间、地点状态、完成标记与已领取标记**。取消未完成工单按明确比例退回原料，已完成工单不能二次领取。
- 例：`小麦×2→面粉×1`（磨坊技能1）；`甘蔗×2→糖×1`（制糖技能1）；`面粉×2+糖×1→面包×2`（烘焙技能2）；`蓝莓×2+糖×1→蓝莓果酱×1`（食品加工技能3）；`铁矿×3+煤×1→铁锭×2`（冶金技能2）；`铁锭×2+木板×1→工具组×1`（锻造技能4）；`布匹×2+树脂×1→船帆×1`（缝帆技能5）。这些数值是默认样例，可通过JSON/ScriptableObject修改。

这里的“时间”是真实世界的时间，分3类：（根据加工公式的不同，提前定义好）
1）玩家当前就在当前界面，亲眼看着它加工，或者在当前城市。时间是秒级：最快5秒，最慢60秒；
2）玩家当前正打开游戏，但没有在当前城市。时间是分钟级：最快5分钟，最慢30分钟；
3）玩家已经退出游戏。时间是小时级：最快2小时，最慢10小时。

**三种真实时间尺度的执行约定**

- 原文三档范围不变，具体订单时长由**配方难度+有效技能**决定，配方存3档时间参数：`foregroundSeconds`（5–60）、`awayCityMinutes`（5–30）、`offlineHours`（2–10）。例如简单面粉=10秒/5分钟/2小时，中等船帆=35秒/15分钟/5小时，高级珠宝=60秒/30分钟/10小时；技能每提高1级可缩短最多2%，但不得低于档位下限。
- 为避免“切换城市或退出重置倒计时”的滥用，同一工单按**状态区间累积进度**：前台/异城/离线分别按对应的归一化速率推进，所有阶段累计到100%即完成。切换场景只改变后续速率，不重新开始也不倒扣既有进度。
- `progress += elapsedRealSeconds / durationForCurrentState`，时间统一用单调计时+持久化UTC墙钟做跨退出恢复；离线时对时间异常跳变设上限并记录修正，避免改系统时间刷产量。离线工单正常完成后，剩余时间不自动无限重开，除非用户显式开启“连续生产”并有足量库存/限额。
- 三档意味着同一批生产在玩家亲临时更快，这属于**陪伴式即时生产与离线回流机制**；UI需要明确显示当前档位、预计剩余真实时间、为何变化。仅改变速度，不改变产物种类或已经抽定的随机结果。
- **生产模块接口**：`IRecipeCatalog`、`IProductionService`、`IInventoryService`、`ISkillResolver`、`IClock`、`IQualityRoller`、`IMarketService`。经济运算不能直接藏在UI事件中；所有服务可用固定种子做无界面单元测试。
- 优先验收：无负库存、切换城市不重置进度、离线再进可结算、不越品质下限、S出现概率随技能合理变化、原料不足不能生产、品质不因随机重载重抽、异常时间无资源复制。

- 玩家从任选家园城市开始，**家园产业园免费自带**，含初始仓库与一个可操作的入门工厂。建议初始金币1,500、基础小型帆船一艘、船舱容量80、少量食水与起始原料；这些为新增初始平衡值，可配置。
- 非家园城市需**亲自到市政厅获得产业许可证**后方可开启产业园。建议解锁费用=300+已解锁外城数×200金币、所需城市声望从0递增到20；玩家应可通过委托或本城交易得到声望，不造成先有工厂才能拿许可证的循环依赖。

- 工厂由玩家拥有，城市不会因为别的玩家拥有工厂而获得该玩家的永久个人技能；“城市拥有该项公式的技能”在首版具体解释为：**玩家在该城市有对应工厂后，该城市的该玩家产业链可以执行相应配方**。未来多人服务器须保持玩家产权和公共城市技能的区别。
- 市政厅、船坞、各交易市场、产业区均为真实可互动地点；事件与价格每城独立保存。城市入口明确展示已解锁建筑、可生产链、声望与仓库状态。

### 四。事件系统

**可插拔任务/事件与连续剧情**

- 主线暂分三章：**第一章《一张旧海图》**（获得家园厂与首条航线）；**第二章《诸港的契约》**（至少开设3座城市的产业园，建立跨城原料→成品链，并招募一名专长伙伴）；**第三章《世界之环》**（寻找三份航路凭证、构建适合远洋的舰队，完成跨海终极航程与商会挑战）。结局为“传奇航路建立”，允许结局后继续自由经营。
- 最终挑战可由4个阶段构成：①探索并记录3条关键远洋航段，②提交从不同港口采购的指定高品质材料，③生产1份最低品质2的“旗舰航海仪”及1套船帆（用已有产业产出组装），④抵达最终目的港；经典模式含一场公平可胜的海盗旗舰战，休闲模式改成暴风/补给航程挑战。胜利字幕、人员结局与通关存档必须真实存在。
- 至少12个可执行事件：初到家园、首次买卖、第一张许可证、首份配方、雇佣伙伴、首次修船、首次遇到逆风、城市缺货、商会急单、海盗遭遇、古地图线索、最终远航；前期事件只出现必要的一部分，避免打断经营。
- 每条事件配置 `eventId / trigger / prerequisites / priority / oneShotOrRepeat / cooldown / dialogue / choices / conditions / effects / nextEvent`，选择产生真切影响（金钱/库存/声望/伙伴/航图/敌对状态），无“点击后什么也没发生”。
- 事件服务通过事件总线监听 `OnCityEnter`、`OnMarketTrade`、`OnProductionComplete`、`OnRouteDiscover`、`OnBattleEnd`、`OnPartnerTalk` 等；用条件判定与冷却去重，不将分支写死在场景对象里。

### 五。航海系统

**航海与探索**

- 采用平面世界航海地图，玩家操控方向、帆角与船速；风向每隔60–180秒平滑改变，风力、洋流、载重、船体状态影响速度。逆风无法直接高速前进，需要迎风转向（tacking），但不能让玩家永久卡死。
- 航行消耗补给、船体耐久；港口可修理、购买食水；航海探索中的「视野」技能提升探测范围，「导航」技能提升航图精度。未探明区域呈现迷雾；到达安全探测半径后发现新港口与航道。
- 每次首次完成两个已知港口之间的有效航行后，可解锁该方向的**已发现航线**。航路本身在存档里持久保存，并提供距离、常见风向、风险、预计耗时。
- 船在海上可遇天气、漂流货箱、海盗/商船、海图事件；可回港、修船或被救援，失败后不应无限软锁。

### 六。航海战斗系统

**可通关2D海战**

- 俯视2D，键鼠控制本舰航向与航速，侧舷火炮有角度、距离、冷却限制；可选择炮击船体或风帆。AI海盗至少会接近、转侧舷、射击、撤离/追击。
- 战斗统计船体、帆、火炮、船员士气与弹药；船体归零=战败或撤离救援，击溃敌舰=胜利与可确认的战利品。遭遇强度与玩家舰队战力挂钩，有教程战。
- **休闲模式没有海战**，海上以缓慢生命/船体耐久损耗和可恢复补给风险替代；主线任务不能要求休闲玩家击沉敌人。**经典模式海战普通难度**。
- 战斗动画关闭时仍执行相同战斗规则，只缩短镜头和特效；不能让“关闭动画”改变战利品或胜负。

**城市场景 HD-2D／移轴镜头美术规范（开发验收重点）**

> 视觉目标：以先前展示的里斯本、威尼斯、杭州三张“八方旅人”式城市参考画面为**视觉方向**，实现可在城市场景中实际移动的 HD-2D 微缩模型质感。先前对话中的三张图片为在线检索展示，并未随当前 Markdown 文件保存为可逐像素测量的原图，因此下述是针对其可见构图特征和同类型 HD-2D 作品的技术拆解，**不是已测得的图片参数**。开发 Agent 应优先读取项目 Assets 中实际参考图，对照截图逐城调校，不得仅套用预设滤镜后宣称“完全一致”。不得直接复制参考游戏受版权保护的图片、场景或角色素材。

**一、从参考画面提炼的可见特征**

- **地形与城市布局**：并非一张完整的平面背景图；场景存在可读的高低差与纵深。街道由地面石板、路沿、台阶、平台、码头岸墙、桥梁、河道或港池组成；建筑立于不同高度的台基上。道路弯折、台阶与桥梁自然引导人物前往地标。里斯本以海港石阶、砖石街道与帆船码头为主；威尼斯以运河、水面、桥与高密度临水建筑为主；杭州以水岸、石桥、院落及传统屋顶为主。三城的具体建筑构图是**设计建议**，须以实际素材参考最终校准。
- **背景图片与景深**：画面最远层是天空、远处海面/河道、建筑剪影或远山；中远层是有体积的街区、桥梁、屋顶和树木；中景是角色、交互建筑入口和可走街道；近景用栏杆、叶片、屋檐、灯笼、船具、招牌等自然遮挡镜头。远近层随镜头运动产生轻微视差，避免“整张城市背景贴图+人物覆盖”的纸片感。
- **画面分层和焦点**：观众视觉焦点稳定落在**可行走中景**，角色、地面行走边界、可点击入口相对锐利；极近的遮挡物和极远背景柔化。过街的建筑阴影、墙根和台阶侧面增强体积感；不是平均模糊整个画面。
- **光影色彩**：暖色主光从一定斜角照入街道，形成建筑与栏杆的方向性投影；背光处仍保留层次。建筑窗户、店铺灯具、灯笼作为局部暖光源；水面有柔和高光。港口可带少量薄雾与水面反光，建筑材质保留像素化纹理，不追求照片写实。
- **环境细节**：画面可见微量漂浮尘埃、海风带动的布旗/树叶、烟囱炊烟、水面波纹和少量反光光斑；粒子只增强生活气息，不遮挡人物和 UI，也不必每一座城市添加同样效果。

**二、场景物体层级与透视方案**

- `CityScene` 保持唯一通用城市场景；运行时载入 `LisbonCity`、`VeniceCity` 等城市根对象，每个城市根对象建议采用 `Terrain`（步行地面/台阶/水岸）、`Architecture`（建筑与桥）、`Background`（远景层）、`Foreground`（镜头近景遮挡）、`Characters`（2D八方向角色/NPC）、`Props`（店招/木箱/植物等）、`Water`、`Lighting`、`VFX`、`NavigationAndInteraction` 分组。分组为**Prefab 子节点，不是额外 Scene**。
- 推荐以**固定倾斜的 3D 空间 + 面向相机的 2D 像素角色**（Sprite Billboard 或按方向选择的精灵片）实现 2.5D。地形、阶梯、桥和建筑可采用低多边形体积、分层 Mesh/Tilemap、像素纹理贴图混合制作。以角色落脚点计算碰撞、遮挡和高度，而非仅以 Sprite 的屏幕 Y 值排序全部物体。
- 摄像机建议使用固定俯视倾角的 Perspective Camera，初始调参范围：俯角约 **30°–45°**（相对于水平面）、FOV 约 **25°–40°**；使用长焦感较强的小 FOV 配合相机距离制造微缩模型效果。数值为制作起点而非截图实测。城市场景内以小范围相机跟随，重点区域允许轻柔构图调整，避免行走时频繁自动旋转镜头。
- 各城必须有真正可走通的行走网格或导航数据，台阶与桥梁的可达性、NPC 与建筑碰撞、遮挡透明/淡出、鼠标点击寻路均可独立测试。视觉台阶不得出现人物“直接穿墙或漂浮”。

**三、深度分层、移轴景深（Depth of Field）与后期**

| 景别 | 典型对象 | 焦点与清晰度要求 | 渲染策略 |
|---|---|---|---|
| 极远景 | 天际线、远山、远海、城市剪影 | 明显柔和、低对比度 | 远景贴图/卡片、多层视差、雾化 |
| 远景 | 远街、屋顶、城墙、港内船只 | 轻到中度虚化 | 真实深度或单独可控背景层 |
| 核心中景 | 角色、道路、台阶、码头及可点击建筑 | **清晰，保持像素轮廓** | 相机焦点跟随角色所在步行平面 |
| 近景 | 栏杆、屋檐、植物、前方帆布等 | 依据深度逐渐柔化，作为画框 | 独立前景层、必要时淡出以防挡住操作 |
| UI | 地标标识、互动提示、交易窗口 | 始终高清且不虚化 | 后期处理之外的 Screen Space UI |

- 使用 URP 下合适的景深能力（依实际 Unity/URP 版本验证可用选项）；可选物理深度驱动 DoF、可控景深遮罩或前/后景分层合成。**仅对屏幕上下边缘施加固定高斯模糊不等于真实移轴效果**：角色爬上台阶、走近桥梁时焦点应随真实深度调整；不能把角色模糊掉。
- 先做正确的几何前后关系和光照，再加 DoF、Bloom、Color Grading、Vignette；避免强景深、高 Bloom、重暗角一起覆盖像素细节。Bloom 只作用于阳光反射、灯具、局部高亮；暗角保持轻微，UI 不受影响。
- 角色 Sprite 采用一致的像素单位、正交采样规则和合适的贴图过滤/抗锯齿方案；对有意的像素边缘保持清晰，背景画面可柔和，但不要出现像素轮廓被非整数放大和图像采样抹花。

**四、光照、材质、天气与粒子分层**

- 每城配置独立 `LightingProfile`、`ColorProfile`、`WeatherProfile`（可用 ScriptableObject 或等价配置）；主方向光及阴影、环境补光、雾色、曝光和局部灯光可以因城市变化，但同一游戏保持统一风格。建筑与地面的阴影方向应一致，人物至少保留接触阴影，避免人物像贴纸悬浮。
- 建筑墙面、石板、木板、瓦片采用像素化或低分辨率绘制纹理，通过法线/几何暗面体现厚度；港口潮湿石面、河水与运河可做控制幅度的高光/反射，不要求昂贵的真实反射。
- 粒子按距离分层：近景偶尔漂过较大的柔光尘点、中景少量细尘/落叶、远景低密度烟雾或海雾；使用 VFX/Particle System 均可，确保不是恒定满屏闪光。风旗、烟、雨、雾与海浪方向受同一城市天气参数驱动。
- 城市建议差异：里斯本偏金黄色斜阳、海风、港口薄雾；威尼斯偏暖色石墙与水面反射、桥下阴影；杭州偏柔和散射光、江南湿润空气和院落层次。属于**视觉美术方案**，不是对先前三张图片天气和时间的精确确认。

**五、实施步骤和验收（1920×1080 / Windows）**

1. 从项目 Assets 指定的截图中提取**构图与调色参考板**：记录地平线、可行走区域、角色在画面中的像素高度、主光方向、最清晰焦平面以及虚化区域；制作里斯本、威尼斯、杭州各一张实际运行截图和参考图并排对照。若参考图未提供，应明确记录“无法进行逐图匹配”，不可宣称画面相同。
2. 先只制作一个可行走的里斯本城市测试区：带高低差的地面、石阶、码头、两栋建筑、前景遮挡、远景层、八方向走动角色；然后完成景深、方向光与少量粒子，确认视觉方案可复用。
3. 使用相同 `CityScene` 控制器和渲染配置体系替换为威尼斯/杭州城市根 Prefab，验证运河桥梁、江南建筑、不同水面/天气效果都能保持统一的微缩模型画风，再扩展到剩余城市。
4. 对每城以玩家走动、NPC 移动、建筑前后遮挡、夜间/阴影环境（若支持）、雨雾/粒子情形进行动态检查；尤其检查**角色始终足够清晰、点击入口可识别、前景遮挡能淡出、台阶无穿模、UI 不被景深处理**。
5. 建议在1920×1080下，以开发环境可稳定达到的目标帧率为性能基线（优先 60 FPS，配置较低时保底 30 FPS），对景深、阴影、雾与粒子设置质量档位；实际性能结论必须通过 Windows 构建运行测试获得。
6. 完成度以**实际运行的城市截图/短录屏 + 参考图对照**验收。开发 Agent 不得以风格描述、概念插画或静态贴图代替可游玩的场景，不得以“添加了 DoF 组件”代替视觉一致性验证。

**市政厅与反馈**

- 每城还须有**市政厅**交互点（外城解锁产业许可证）及至少一个用于伙伴/事件的公共地点；城市名、方位、可用市场、当前任务、船只停泊位置始终可查。
- 市场列表显示商品类别、品质、玩家库存、城市供给趋势、即时买价/卖价、数量与交易后预计价格；交易时滑块/数量键不可超过金币、容量、实际库存。所有按钮反馈明确。

### 四。产业区界面

一片跟当前城市同样风格的，但是初始是一片空地的界面。没有玩家在界面上跑动。

显示当前创建好的工厂，鼠标hover可以显示工厂的级别、当前是否在生产。

每个产业区默认有一个 “仓库”，玩家可以往里面放商品，供工厂生成时使用，也生产后放置产品。

**工厂/仓库UI**

- 建筑位显示建造费、工厂等级、可执行配方、有效技能来源、输入库存、单次产量、预计品质概率、三档时长、当前订单状态；将“可生产”与“原料不足/等级不足”区分提示。
- 仓库支持船舱↔城市仓库双向运输、按类别/品质筛选、原料保留数量、生产自动续单开关、市场自动出售策略；仓库转移不得与工厂预留库存发生双重扣除。

### 五。自动航线地图界面

展示一个缩小版的世界分海域地图，用于集中查看航线、舰队、城市供需与自动运输情况。该界面的视觉布局与信息组织参考素材文件夹中的 **AutoSailing Map pack**，但需要与本项目整体像素 UI 风格统一。

**界面内容与显示规则**

- 地图按海域分区显示，例如近海、西洋、印度洋、东亚海域等；已探索海域正常显示，未探索海域以迷雾或暗色遮罩显示。
- 各个城市在地图上显示为不同大小的圆点：家园港、已解锁港口、普通已知港口、任务关键港口使用不同尺寸或描边区分。
- 地图上实时显示玩家舰队与自动舰队的位置、朝向、所属航线、当前状态（航行中／装货中／等待中／返航中／受损中）。
- 已知航线以细直线显示，当前选定航线高亮显示；自动贸易中的活跃航线需额外显示方向箭头。
- 点击城市圆点后，右侧或下方信息面板显示该城市当前可交易商品、价格、供需趋势、库存概况、城市特产、城市增益、已建工厂、仓库存量与许可证状态。
- 点击舰队图标后，显示舰队名称、旗舰、载货清单、剩余补给、目的地、下一站、预计到达时间、当前任务与最近一次盈亏记录。

**主要功能**

- 快速查看所有已知城市的商品信息与供需状态，而不必逐城进入市场界面。
- 创建、查看、修改、暂停或删除自动贸易航线；可直接从该界面为某支舰队指定出发港、目的港、运输商品、数量上限、最大买价、最低卖价、补给策略与循环次数。
- 支持按商品类别、城市、海域、舰队状态进行筛选；例如快速筛出“原料短缺城市”“高利润成品目的地”或“当前空闲舰队”。
- 支持在地图上选择两座城市后，快速查看该航线的预计距离、常见风向、风险等级、平均耗时、最近盈利情况，以及是否已满足自动通航条件。
- 支持快捷跳转：从该界面可直接跳转到城市界面、港口码头、船坞界面、产业区界面或舰队详情界面。

**交互与验收要求**

- 自动航线地图界面主要承担“战略总览”功能，不替代城市内跑图和市场交易界面的细节交互。
- 所有地图信息必须与真实游戏状态同步，不能只显示静态示意图；舰队位置、城市库存、航线状态变化后应及时刷新。
- 当某条自动航线因缺货、亏损超限、船只受损、补给不足、港口未解锁等原因暂停时，地图界面要有明确图标和文字提示。
- 该界面必须支持鼠标缩放、拖动浏览、悬停提示与图例说明；信息密集时应优先保证可读性，避免遮挡。
- 若后续扩展多人模式，该界面保留显示其他玩家商队或公共航线的扩展位，但首版单人模式默认只显示玩家自己的舰队与航线。

### 六。航海界面

玩家在航海界面可以操作船帆，根据各种变化的风向，航向地图上的位置（参考大航海时代4）。自动航线地图界面负责总览与调度；航海界面负责实际手动操控、探索、补给风险与即时事件处理。

### 七。存档／读档界面

- 独立的 `SaveLoadScene`，负责七个存档槽位的创建、浏览、保存、读取、覆盖确认和异常存档提示。可从标题及游戏内暂停菜单进入，并保留返回来源，以便完成操作后正确返回。
- 该场景只操作 `Core/SaveSystem` 中的存档数据与摘要，不维护第二份世界状态；存档槽显示的信息、自动存档与手动存档规则遵循前述“存档规范”。

### 八。世界地图总览界面

- 独立的 `WorldMapScene`，以世界范围展示海域、已知／未知城市、探索进度、当前位置和已发现航路，主要用于战略浏览、地理定位和主线探索目标查看。
- 与 **自动航线地图界面** 明确分工：`WorldMapScene` 面向世界地理与整体探索；`AutoSailingScene` 按海域聚焦舰队、城市商品供需及自动航线配置。两者可共享地图底图和城市定位数据，但拥有独立的 UI 和交互逻辑。
- 在世界总览上选择城市时可查看基础资料，并跳转至相关详情；不可绕过航路探索和舰队条件直接瞬移、交易或调度。

## Unity Scene 划分、命名规范与工程目录（必须遵守）

**核心原则：恰好以下八类功能主 Scene；不为每座城市单独创建 Unity Scene。** 首版可按每类一个 `.unity` 场景组织，城市差异由配置和动态加载的城市内容实现。菜单弹窗和建筑交互可做为共享 UI／Prefab，不因一个面板就额外建立主 Scene。

| Scene 文件名 | 对应功能 | 内容／切换原则 |
|---|---|---|
| `MainMenuScene.unity` | 开场场景 | 标题演出、新游戏、读档入口、设置和退出；负责进入存档界面或角色创建。 |
| `SaveLoadScene.unity` | 存盘读盘场景 | 七个槽位、存档摘要、保存／读取／覆盖确认和返回来源。 |
| `CharacterCreationScene.unity` | 人物创建场景 | 模板选择、外观编辑、角色预览、出生城市选择。 |
| `CityScene.unity` | 城市场景 | 角色八方向移动；按城市配置加载地形、背景、建筑、地标、NPC及事件。 |
| `IndustryScene.unity` | 产业园场景 | 按当前城市加载工厂布局、仓库、生产信息和建设交互。 |
| `SailingScene.unity` | 航海场景 | 玩家实际操帆、航向控制、探索、天气与航行事件；海战可在此使用独立战斗控制模式／UI，而非首版第九个主 Scene。 |
| `AutoSailingScene.unity` | 自动航行配置场景 | 按海域的缩小地图、舰队位置、货物与城市供需、已知／选定航线和自动贸易任务管理；参考 `AutoSailing Map pack`。 |
| `WorldMapScene.unity` | 世界地图总览场景 | 全世界范围的海域、城市、已探索区域和航线总览；不与自动航行配置功能混同。 |

**命名约定**

- 所有 Unity Scene 的文件名及主 Scene 类型名均以 `Scene` 结尾，例如 `MainMenuScene`、`CityScene`、`AutoSailingScene`；不使用 `City.unity`、`Sailing.unity` 等含混名字。
- 城市内容、城市配置和城市专属资源的**城市标识名**均以 `City` 结尾，例如 `LisbonCity`、`VeniceCity`、`HangzhouCity`。可以有 `LisbonCity.asset`（配置）和 `LisbonCity.prefab`（城市地图根对象）；引用用稳定 `cityId`，不得以场景名充当城市名。
- Prefab 的名称**不需要**以 `Prefab` 结尾：例如 `Harbor`、`CityHall`、`MarketStall`、`LisbonCity`；仍使用 Unity 规定的 `.prefab` 扩展名。专门区分用途时可按明确功能命名，但不要强制加 `Prefab` 后缀。
- 通用系统代码、配置和存档逻辑不得以 `Scene` 对象名称为主键。城市场景实例在退出／卸载时可以销毁，世界状态必须仍可持续运算并可保存。

- 城市地图、地形与背景、建筑、调色板、天气和背景音乐允许每城独立制作，但**码头、船坞、市场、市政厅、产业园、NPC 和事件必须符合统一交互接口**。城市特有事件可以配置替换或扩展，不复制整套场景控制逻辑。

- `Resources/` 在这里是用户要求的资源分类目录。若实际采用 Unity `Resources.Load`，应注意打包与内存管理约束；大量按需加载的图片/音乐也可以用 Addressables 或直接序列化引用管理，但目录名及资源职责保持清晰，不要求所有资源都经 `Resources.Load`。

## 游戏数据、公式与用户数据分层（2026-10-15 重构）

本节是用户确认的项目设计规则。出厂游戏数据与用户写入数据分别管理，后续修改须沿用这一边界。

### 出厂游戏数据

`Assets/Resources/Data/` 是游戏内容与可调数值的主目录。所有商品、配方、角色/伙伴、船型、升级参数、初始值、品质概率参数、城市加成和公式系数均使用 JSON；禁止在 Core 的 DTO 字段初始化器或业务分支里补上隐藏的平衡数值。数学恒等值、索引步进、单位换算、PRNG 位移、存档协议版本及既有品质编码属于代码/协议常量，不是游戏平衡数据。

- `manifest.json`：版本、分类文件清单与单文件字节上限，当前上限为16 KiB。超过上限须继续按产业、城市或事件拆分。
- `Products/`、`Recipes/`：按产业拆表；`order.json` 固定全局顺序，保留旧存档中的商品索引含义。不要通过调整文件加载顺序改变现有编号。
- `Cities/`：港口和原料分布、各城生产费用/时长倍率、工艺与品质加成。
- `Characters/`、`Ships/`、`Skills/`、`Industries/`、`Events/`、`Quests/`：内容定义与任务引用；事件按条目拆文件。
- `Economy/market.json`：市场规则和城市初始库存数量及比例。
- `Initial/`：人物/游戏初始状态、仓库、船、伙伴、自动航线、外观与出厂设置。由状态工厂复制生成独立实例，不能修改共享模板。
- `Balance/`：经济、生产、品质概率、导航、世界时钟、技能、升级、舰队、战斗、任务、事件和界面操作参数。城市特殊加成放在对应城市数据中。
- `Presentation/Atlases/`：图集切片等现有 JSON 元数据；迁移时保留 Unity GUID。
- `Schemas/`：标准 JSON Schema、运行时参数约束及索引。字段名称、类型、范围、必填项须同步维护。运行时校验参数和跨表引用；离线校验所有登记的数据文档及文件大小。

### 代码与公式

业务代码、数据结构、Loader/Saver、校验与状态创建位于 `Assets/Core/`。公式实现统一收拢到 `Assets/Core/Data/Formulas/`，共享公式在 `Assets/Core/Data/GameFormulas.cs`。公式结构作为代码审查，系数、等级阈值、概率系数和奖励数量从数据读取；不从 JSON 执行任意 C# 或表达式脚本。

`CatalogLoader.Load()` 是唯一主目录加载入口，读取 manifest 并合并分类文件。缺文件、重复配置、未知参数、非法数值、无效商品引用或无法匹配的顺序表应明确失败，不能悄悄恢复为硬编码默认值。新游戏入口为 `Assets/Core/Data/GameService.Initialization.cs`；`StateFactory` 复制出厂初始数据。旧存档加载不走新游戏初始化。

表现层继续承担 Unity 场景、输入和绘制，调用 Core 的公式与服务；战斗伤害、市场价格及其他可调玩法参数不得另存一套 UI 数值。iOS/IL2CPP 下用 `Core/Data/link.xml` 保留反射与序列化需要的数据类型。

### 模拟与测试数据

模拟种子、采样次数、资金夹具、时间步长和测试阈值放在 `Assets/Tests/Data/` 的 JSON 中，测试逻辑位于 `Assets/Tests/`。已抽离原先 UI 文件内的 SmokeStep 测试逻辑。测试配置不进入生产 Resources/Data；开发验收包通过构建脚本把测试夹具复制到独立的 `TestData/`。测试数据加载支持 `MARITIME_TEST_DATA` 指定目录。

`Core/Simulation/` 是真实游戏的工作流调度，不是测试模拟；世界时间和补货参数来自 `Resources/Data/Balance/`，不能把运行时必需参数放进 Tests。算法中的0/1、数组索引和测试状态机分支编号可保留在代码中。

### 用户写入数据（不属于出厂游戏数据）

所有存档和用户修改后的 settings 都在 Unity 引擎提供的 `Application.persistentDataPath` 下，统一由 `Core/SaveSystem/UserDataPaths.cs` 定位：

- `Saves/slotN.json`、`slotN.auto.json`：玩家状态；`.bak` 为备份。保留既有 Saves 路径，避免本次数据拆分导致旧档丢失。
- `Settings/user.json`：独立用户设置，`.bak` 为上次设置备份。出厂设置只在 `Resources/Data/Initial/settings.json`。设置关闭、应用暂停/退出时持久化，测试使用隔离目录。
- 写入使用临时文件后替换正式文件，保留备份。旧存档里已有 settings 字段继续保留以兼容；存在独立设置文件时优先使用独立文件，尚无独立文件时可读取旧档设置。

不得将用户写入数据放在 Resources、Assets、游戏安装目录或应用 bundle 内；不得硬编码 Windows 用户名或 iOS 沙盒 GUID。Windows 的引擎路径通常为 `%USERPROFILE%/AppData/LocalLow/<company>/<product>`；iOS 由 Unity 返回应用沙盒 Documents 路径。维持应用标识稳定，平台变更时不要根据字符串猜测目录。

Steam Cloud 是发布平台配置，不会因为使用 persistentDataPath 就自动启用。Windows Auto-Cloud 可使用 `WinAppDataLocalLow` 根目录配置 `MaritimeLegend/航海世家/Saves`；应按平台配置路径映射，排除临时文件、日志和设备相关设置。尚未在 Steam 后台启用或完成跨设备验收；iOS 持久化路径也不等同于已实现 iCloud 游戏存档同步。

官方依据：[Unity persistentDataPath](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Application-persistentDataPath.html)、[Steam Cloud](https://partner.steamgames.com/doc/features/cloud)、[Apple File System Basics](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemOverview/FileSystemOverview.html)。
